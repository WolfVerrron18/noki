# Манифест Nidoki

Правила проекта. Обязательны для любого кода. Новое правило — дописываем сюда.

Telegram Mini App для записи к мастеру красоты. Аудитория — девушки: интерфейс милый, пастельный, с маскотом Ноки (котёнок-облачко, `components/mascot/NokiMascot.vue`). Что сделано и что дальше — `docs/STATUS.md`, как запустить — `README.md`.

Приложение для **любых** бьюти-мастеров: маникюр, визаж, брови, ресницы, массаж и т. д. Ни маскот, ни тексты, ни примеры не привязываем к одной специализации (никаких флакончиков лака, «маникюра» в плейсхолдерах и т. п.).

Стек: Vue 3 + Vite + TS + Pinia + Vue Router + vue-i18n + SCSS; бэкенд — Node.js + TypeScript (Hono, Drizzle, zod) и PostgreSQL (локально и в тестах — PGlite); деплой — VPS + Nginx (сертификат уже есть, Caddy не используем).

## 1. Цвета

- Цвет называется **по назначению**, а не по виду. Никаких `pink`, `lightGray`, `mainVeryGrayColor`.
- Семейства: `primary`, `secondary`, `cute`, `success`, `warning`, `danger`, `neutral`.
- У каждого шкала `100…900`: чем больше число, тем цвет «грубее».
  - `100–300` — полупрозрачные оттенки базы (подложки, бейджи, мягкие фоны);
  - `400` — светлее базы, `500` — база;
  - `600–900` — темнее, `900` — самый тёмный (например, `danger-900` — бордовый).
- `neutral` — фоны и текст: `neutral-100` ≈ фон, `neutral-900` = основной текст. В тёмной теме шкала зеркалится, поэтому смысл чисел сохраняется.
- Используем `var(--primary-500)` и семантические алиасы. Алиас заводим, только если значение зависит от темы или подменяется Telegram: `--bg`, `--bg-card`, `--text`, `--text-muted`, `--on-primary`, `--shadow`, `--overlay`.
- Текст на мягкой подложке `-100` (бейджи, плашки) — только `var(--<цвет>-on-soft)`: в светлой теме это 700, в тёмной 400. Голые `-700`/`-800` для текста не используем — в тёмной теме они не читаются.
- Хардкод hex в компонентах запрещён. Новый цвет — только в `src/styles/_palette.scss` (`$palettes` — акценты тем, `$status` — состояния).
- **Цветовые темы мастера** (`masters.theme`, `EnumPalette` в `src/styles/palettes.ts`): тема меняет `primary` и `cute`; `secondary` в каждой теме равен `primary` — интерфейс в один цвет темы, второй акцент не вводим, а `neutral` подкрашивается под неё автоматически; `success`, `warning`, `danger` общие. Тема ставится атрибутом `data-palette` на `<html>` — только в `App.vue` (кабинет — тема мастера или примерка `themePreview`, страницы `/b/:slug` — тема мастера из ссылки). `data-palette` на любом элементе даёт ему цвета своей темы (образцы в «Оформлении»). Компоненты пишут `var(--primary-500)` и про темы не знают. 500 каждого акцента должен читаться с белым текстом не хуже текущего розового. Новая тема: `$palettes` → `EnumPalette` → перевод `theme.palette.<id>` → значение в миграции.
- Где alpha-оттенок просвечивает (наложение фигур в SVG), смешиваем токены через `color-mix()`, а не берём `100–300`.

## 2. Стили

- Только SCSS: `<style scoped lang="scss">`.
- Переменные разнесены по файлам в `src/styles/`:
  - `_palette.scss` — базовые цвета и генерация шкал;
  - `_theme.scss` — вывод шкал и алиасов, светлая и тёмная темы;
  - `_geometry.scss` — отступы `--space-*`, скругления `--radius-*`, размеры `--control-height`, `--container-width`;
  - `_typography.scss` — `--font-family`, `--font-size-*`, `--font-weight-*`, базовые стили заголовков;
  - `main.scss` — только собирает их, плюс reset и утилиты.
- В компонентах не пишем голые px для отступов, скруглений и шрифтов: берём переменные. Исключение — внутренние координаты SVG.
- Тема (светлая/тёмная) берётся из Telegram (`data-theme` на `<html>`), фон и текст — из `themeParams` через `--tg-*`. Пользовательница может выбрать её вручную (`NokiSchemeSwitch`: «Оформление» и «Мои записи», хранится на устройстве); тогда цвета Telegram берутся, только если его тема совпадает с выбранной.
- Отмена и удаление — `NokiButton variant="outline"`: контур и текст цветом темы, без заливки. Красный не используем — выбивается из пастельных тем; такие действия всё равно спрашивают подтверждение.

## 3. Компоненты и типы

- Базовые компоненты называются с префиксом `Noki` (`NokiButton`, `NokiInput` …). Префикс `Cute` больше не используем.
- Главное действие экрана — `NokiMainButton` (в Telegram это нативная MainButton внизу, в браузере — кнопка, закреплённая внизу экрана). **В каждый момент на экране ровно одна**: если вложенный компонент выводит свою (например, календарь в режиме выбора дней), он сообщает об этом через `v-model:busy`, и родитель свою прячет.
- Экран = закреплённая шапка (`PageHeader`: где я и «назад») + закреплённая главная кнопка снизу. Кнопку не прячем в конце длинной формы.
- Правка существующего (профиль, часы, оформление, своя услуга): «Сохранить» неактивна, пока форма совпадает с сохранённой, — `useDirty` (`dirty`, `markSaved` после сохранения, `confirmLeave` на «назад»: с изменениями спрашивает, уйти ли). Создание нового (новая услуга, запись) — кнопка активна сразу, по нажатию показывает, что заполнить. Реакция на сохранение (Ноки радуется) должна быть видна: если Ноки выше кнопки — докручиваем к ней.
- Развилка режима, где второй вариант легко не заметить (график «каждую неделю / по датам», «по часам / точное время»), — `NokiChoiceCards`: карточки с пояснением у каждого варианта. Короткие однородные варианты — `NokiSegmented`.
- Короткие действия поверх экрана — `NokiSheet` (шторка снизу). В шторке быстрые варианты применяются одним тапом, а «своё значение» — через главную кнопку шторки.
- Часы одного дня — `DayHours` (начало, конец, список перерывов) из `@/utils/hours`; в данных это интервалы (`toRanges` / `fromRanges`), проверка — `validateDayHours`. Перерывов сколько угодно (`PauseList`), они всегда отсортированы (`sortPauses`). Новый перерыв — только `suggestPause()` (null — места нет, кнопка неактивна); смена начала переносит перерыв целиком, смена конца меняет длительность (`setPauseEdge`).
- Быстрые варианты часов — только шаблоны, которые мастер создала сама (`masters.hour_templates`). Свои «стандартные» варианты не подсовываем: у мастера может быть ночной или любой другой график.
- Календарь месяца — один компонент `NokiCalendar` (сетка, навигация, выделение, оформление клетки через `toneOf`, содержимое — слот `#day`). Им пользуются и редактор графика, и просмотр записей; новую сетку месяца не верстаем.
- Подсказки — `useHint` (tippy.js): без hover, сами показываются один раз при первом знакомстве, дальше — по кнопке «?». Постоянные плашки-инструкции не ставим.
- Тур — первое знакомство с экраном: `useTour` + `NokiTour` (один на всё приложение, в `App.vue`). Вид — карточка, закреплённая внизу экрана (крестик, «Назад / Дальше» всегда видны, длинный текст прокручивается внутри), и мягкая обводка у элемента шага (`data-tour-active`, стиль в `main.scss`); затемнения и «окошка» нет. Шаги — в `src/components/tour/tours.ts`, цель шага — элемент с `data-tour="…"`, тексты — `tour.<тур>.<шаг>`. Тур сам запускается один раз (`autoStart` на экране), повторить — кнопка «Как это работает» справа вверху (`PageHeader :help`, на главной — `NokiHelpButton`); ссылки внизу экранов не ставим. В карточке есть слот `#noki` — Ноки нарисуем позже. Точечные «?» (`useHint`) остаются для деталей внутри экранов.
- Тур-пример: шаг может сам показать дело (`action` в шаге + `TourActions` в `start`) — Ноки жмёт настоящие кнопки и печатает через `@/components/tour/robot` (`robotTap`, `robotType`, `robotWait`). «Дальше» доводит действие до конца сразу, «Пропустить» — бросает, «Назад» — останавливает и отменяет действие шага: экран передаёт в `start` `TourUndo` (`save` — снимок перед действием, `restore` — вернуть его), в снимок входит всё, что меняет Ноки (и выбор дней в календаре). Действие стартует, когда тур докрутил экран до элемента (`ready`). Пример ничего не сохраняет: после тура экран возвращает форму к началу. Такие туры: «Как добавить услугу» (`SERVICE_DEMO_TOUR`, сам — при первой услуге) и «Часы работы» (`HOURS_DEMO_TOUR`, сам — при первом заходе на экран); на обоих экранах ссылка «Показать на примере» (`tour.demo`). Шторку поверх тура не открываем: поле времени Ноки только «нажимает» (`robotPress`), значение экран ставит сам. Протягивание — `robotDrag`: кружок-«палец» поверх затемнения и настоящие pointer-события в контейнер; так устроен тур «По датам» (`DATES_DEMO_TOUR`, сам — при первом переключении на «По датам»). Поэтому то, что ищет элемент под пальцем, ищет его сквозь слои (`elementsFromPoint`), как `NokiCalendar`.
- Блок, который появляется и пропадает по состоянию внутри формы (ряд подсказок, своё значение), — `NokiCollapse :open`: плавно меняет высоту вместо скачка.
- Интерфейс не должен «прыгать»: элементы, которые появляются по состоянию (выбор, статус), занимают заранее зарезервированное место, а главная кнопка меняет подпись, а не появляется вторая.
- Категория услуги — справочник `EnumServiceCategory` в `src/components/services/category.ts` (значения хранятся в `services.category`, не переименовываем). Иконки — `src/components/services/icons/<Name>Icon.vue` (корень `<g>` с одними контурами, viewBox 0..24, без своих стилей), реестр «enum → иконка + ключ i18n» — `services/registry.ts`, показ — `ServiceCategoryIcon`. Новая категория: enum → иконка → реестр → перевод `services.category.<id>`, база не меняется. Одна категория на услугу; маникюр и педикюр — одна категория, стрижка и окрашивание — «Волосы».
- Типовые услуги категории — `SERVICE_PRESETS` в `src/components/services/presets.ts` (id + длительность, перевод `services.preset.<id>`): только самые частые услуги, подсказка при создании новой услуги заполняет название и длительность, цену — никогда.
- Порядок услуг — поле `sort`, меняется только через `reorderServices` (в сторе `moveService`; на экране — перетаскивание за ручку, `useDraggable` из vue-draggable-plus, ручка с `data-no-press`); списки всегда в порядке мастера.
- Телефон вводится только через `NokiPhoneInput`: код страны («+7») стоит перед полем всегда, в поле — номер с маской; вставка в любом виде («8 927…», «7927…», «+7 (927)…», «8-(927)-…») раскладывается `splitPhone()`; `telegram` — кнопка «Взять номер из Telegram», когда номер вводят о себе. Страна для номеров без «+» — `phoneCountry(master.timezone)`. Перед отправкой — `normalizePhone()`, в данных номер всегда в E.164, показ — `displayPhone()`. Сервер нормализует так же.
- Порядок блоков в `.vue`: `<template>`, затем `<script setup lang="ts">`, затем `<style scoped lang="scss">`.
- У экрана ровно один корневой элемент, и комментарий в шаблоне — только внутри него: комментарий перед корнем делает корень фрагментом, и `<Transition mode="out-in">` в `App.vue` зависает — следующий экран не появляется.
- Пропсы, события и v-model описываются именованными интерфейсами (`interface Props`, `interface Emits`), а не инлайн-объектом в `defineProps<{…}>()`.
- JSDoc обязателен у каждого интерфейса, типа, поля интерфейса, пропса, события, `defineModel` и метода публичного интерфейса (с `@param` / `@returns`, где это не очевидно).
- Общие типы UI — в `src/components/ui/types.ts` (например, `SelectOption<T>`); типы данных — в `src/api/types.ts`. Не дублируем одну форму под разными именами.

### Маскот

- Ноки — только Rive (`src/components/mascot/rive/NokiRive.vue`, файл `public/rive/noki_rebuilt.riv`, контракт ViewModel `Character` — `rive/character.ts`). SVG-версии нет; недостающие детали дорисовываем в Rive.
- `NokiMascot` принимает `mood` (настроение), `greet` (реакция при появлении), `phone`; реакции — через `ref` (`react`, `phone`).
- **Конструктор внешности** (`look`): слои `fur`, `background`, `head`, `neck`, `badge`. Пока в Rive есть только `head` (шапки), конструктор показывает только готовые в Rive слои.
  - id деталей — строковые enum'ы `EnumMascot*` в `src/components/mascot/look.ts`. Их значения хранятся в базе (`masters.mascot`), существующие не переименовываем.
  - Реестр «enum → состояние в Rive» — `src/components/mascot/registry.ts` (например, `MASCOT_HEAD` → `EnumNokiHat`), подпись — `mascot.hat.<id Rive>`.
  - Новая деталь: значение в Rive-файле и в `rive/character.ts` → значение в enum `look.ts` → строка в реестре → перевод. База не меняется.
  - Данные из базы всегда проходят через `normalizeLook()`: неизвестный id не ломает отрисовку.
  - Значок (`badge`) — единственное место, где допустимы предметы конкретной специализации (лак, кисть, ножницы).
- У каждой анимации есть отключение в `prefers-reduced-motion`.
- Витрина всех настроений и шапок: `/dev/mascot` (только `npm run dev`).

### Стиль рисования (маскот, гардероб, персонажи)

Только для Ноки и того, что на нём. Интерфейс маскоту не подчиняется: иконки — см. «Иконки интерфейса» ниже.

Мультяшно, а не реалистично. Эталон — сам Ноки. Правила одинаковы для SVG и Rive:

- **Контур.** У каждой фигуры заливка-пастель и контур того же тона, темнее заливки (как у Ноки `#ffd6e5` / `#f2a7c3`). Силуэт — 3px, внутренние детали — 2px (в масштабе Ноки 200×200). Тоньше 1.5px не рисуем. Стыки и концы линий круглые. Чёрный и тёмные контуры не используем, тёмный `#3a2a3e` только для лица.
- **Ни одного острого угла.** Все углы скруглены (минимум 2–5px). Острые кончики (колпак, корона, ушки) заканчиваются шариком или мягким скруглением.
- **Пропорции.** Формы крупные и простые, аксессуары чуть больше реального размера (гардероб масштабируем примерно в 1.25 раза относительно головы). Немного наклона и асимметрии для живости.
- **Минимум деталей.** На предмет одна-две внутренние детали (складка, пятнышки, помпон), без мелкой штриховки, текста и «реалистичных» складок ткани.
- **Объём.** Ноки круглая, поэтому вещи на ней тоже не плоские. Свет всегда сверху слева:
  - блик — один мягкий белый полупрозрачный овал сверху слева;
  - тон тени — та же заливка, чуть темнее, на правой стороне или нижней грани (у оригами — правая грань сгиба);
  - облегание — нижний край вещи изогнут «улыбкой» вокруг головы, края ниже середины; ленты, отвороты, рубчики идут по тому же изгибу;
  - вид чуть сверху — поля и ободки рисуем эллипсом, видна задняя стенка или верх (крышка цилиндра, задний край короны);
  - контактная тень — под вещью на голове мягкое пятно цвета контура Ноки (~45%), чтобы вещь лежала, а не висела.
- **Цвета.** Только из палитры маскота: pink, coral, yellow, lilac, blue, mint, paper. Новый цвет — пастельная пара «заливка + контур».
- **Посадка.** Головной убор рисуем вокруг точки (0,0) = макушка Ноки (100, 56.5) и проверяем на точном контуре головы (артборд `Hats` в Rive).

### Иконки интерфейса

- Линейные, спокойные, женственные: один контур `stroke-width: 1.5` в viewBox 24, скруглённые концы и стыки, без заливки, бликов и теней. Цвет — `currentColor` (по умолчанию `--primary-500`).
- Плавные изогнутые линии вместо грубых геометрических; акцент — маленькая искорка или сердечко, не больше одного-двух на иконку.
- Деталь, которая в 20px сливается в пятно (мелкие лепестки, точки), не рисуем.
- Новые иконки сначала показываем на утверждение по одной-две, потом добавляем в код.

### Анимации (GSAP)

- GSAP подключаем только через `@/animations/gsap`; каждая анимация проверяет `prefersReducedMotion()`.
- Рассчитываем на телефон: только pointer-события, без hover. Ничего важного не прячем за анимацией.
- Горизонтальный ряд вариантов, который не влезает, — `NokiSegmented scroll` (Embla, `dragFree`): тянется пальцем и мышью с инерцией. Свою прокрутку рядов не пишем.
- Пункты меню-навигации — `v-fill` (заливка цветом темы от точки входа мыши или касания, стекает к точке ухода) вместе с `v-press`.
- Нажимаемое — `v-press` (желейное нажатие, `{ depth }` для мелких элементов). CSS `:active` с transform и `transition: transform` на таких элементах не используем — конфликтуют с GSAP.
- Выбор (слот, день, вариант) — `v-pop="выбрано"`. Иконка категории при выборе прорисовывается заново (`ServiceCategoryIcon :active`, `drawIcon`), искорки в иконках помечаем классом `spark`. Списки — `useStaggerIn(ref, trigger)`. Праздник — `<NokiConfetti>` внутри элемента с `position: relative`.
- Маскот: «буп» по тапу — триггер `boop` в Rive. Внутри кнопок — `:boop="false"`.

## 4. Импорты

- Внутри `src` импортируем только через алиас `@/` (`@/components/ui/NokiButton.vue`), относительные `./` и `../` не используем. Исключение — `@use` между партиалами в `src/styles/`.

## 5. Тексты и i18n

- Ни одной строки текста в шаблонах и сторах — только `const { t } = useI18n()` и `t('section.key')`.
- Локали: `src/i18n/locales/ru.ts` — эталон (тип `Messages`), остальные (`en.ts`) типизированы по нему, поэтому пропущенный ключ — ошибка компиляции.
- Сторы и API возвращают **ключ** i18n (например, `auth.failed`), текст подставляет экран.
- Язык: параметр `?lang=en` в адресе (для проверки), затем `language_code` из Telegram, затем браузер, фолбэк — `ru`.
- Цены — только через `useFormat().price()` (Intl с валютой `CURRENCY`), не склеиваем символ валюты в переводах.
- Бот тоже будет мультиязычным: тексты уведомлений держим в словарях, не в коде хуков.
- **Без эмодзи** в подписях, кнопках и текстах.

## 6. Роутинг

- Папка `src/router/`. `router.ts` только собирает модули.
- Каждый раздел — свой файл `<section>Router.ts`, экспортирует `RouteRecordRaw[]` (`masterRouter.ts`, `clientRouter.ts`, потом `categoryRouter.ts` и т. д.) и подключается спредом в `router.ts`.
- У каждого маршрута есть `name`. Переходы делаем по имени (`router.push({ name: 'master-home' })`), а не по строке пути.
- Префиксы: мастер — `/m/*`, клиентка — `/b/:slug/*`.

## 7. Данные на фронте

- Экраны и сторы не ходят в API напрямую, только через `repo()` из `@/api/repo`. У интерфейса `Repo` две реализации: `apiRepo` (наш сервер) и `mockRepo` (localStorage, для режима просмотра без бэкенда). Новый запрос: метод в `Repo` → эндпоинт на сервере → вызов в `apiRepo` и поведение в `mockRepo`.
- Запросы к серверу разложены по разделам в `src/api/services/` (`auth`, `masters`, `services` — услуги, `slots`, `appointments`, `feedback`), каждый — объект `<раздел>Api`; `apiRepo` только собирает их. Сам запрос — `api()` из `@/api/http` (токен, JSON, ошибка со `status`), `fetch` в разделах не пишем.
- Типы сущностей — в `@/api/types.ts`.
- Повторяемая логика экранов — в `src/composables/use*.ts` (форматирование, ссылки и т. п.).
- Базовые UI-компоненты — `src/components/ui/Noki*.vue` и `PageHeader.vue`. Новые экраны собираем из них, а не верстаем поля заново.
- Нативные контролы, которые рисует система, не используем: выбор из списка — `NokiSelect` (поле + шторка), число — `NokiNumberInput` (только цифры, единица после числа, по желанию − / +; тап по левой половине поля — минус, по правой — плюс), а не `<select>` и `type="number"`. Цена — `NokiNumberInput currency` (разряды и знак валюты по Intl) с быстрыми прибавками `quick`.

### Даты и время

- Только dayjs, подключённый через `@/utils/date` (плагины utc, timezone, customParseFormat настроены там). Сам `dayjs` напрямую не импортируем.
- День — строка `YYYY-MM-DD` в поясе мастера (`DAY_FORMAT`), момент — ISO в UTC.
- Время всегда показываем в поясе мастера (`master.timezone`, у записи — `master_timezone`), не в поясе устройства.
- Расчёт слотов — `freeSlots()` в `@/utils/slots`; сервер импортирует этот же файл (не копию) и окончательно проверяет запись.
  - Клиентке: не раньше чем через `MIN_LEAD_MIN` и с фильтром пустых окон (`minServiceMin` — самая короткая активная услуга: в каждом свободном окне остаются начала с наименьшими потерянными минутами). Мастеру при ручной записи — вся свободная сетка.
  - Запись принимается, только если её начало есть в `freeSlots()` с теми же настройками (а не просто не пересекается с другими).
  - Момент из часов мастера собираем из строки `дата + ЧЧ:ММ` в его поясе, не прибавляем минуты к полуночи (день перевода часов).
- График мастера: `schedule_mode` — `weekly` (шаблон `work_hours` по дням недели) или `dates` (рабочие дни отмечены в календаре). `day_overrides` — часы на конкретные даты: в `dates` это сами рабочие дни, в `weekly` — исключения из шаблона. Рабочие часы дня — только через `rangesFor()` / `isWorkDay()`, не читаем `work_hours` напрямую.
- Как записываются клиентки: `slot_mode` — `grid` (часы + шаг `slot_step_min`) или `fixed` (точные времена начала, которые мастер задала сама). Времена — `work_slots` (по дням недели) и `slot_overrides` (на даты) с той же логикой weekly/dates, шаблоны — `slot_templates`. Времена дня — только через `startsFor()`; рабочий ли день — только `isWorkDay()`, он учитывает режим. Редакторы те же (`WorkHoursEditor`, `MonthScheduleEditor` с `fixed`), день с временами — `DaySlotsForm`, утилиты — `@/utils/daySlots`.
- Внешность Ноки на экранах берётся из контекста (`NOKI_LOOK_KEY`): App даёт Ноки текущего мастера, `BookingLayout` — Ноки мастера, к которому записывается клиентка. Явный `:look` нужен только в превью конструктора.

## 8. Безопасность и данные

- Вход только через Telegram: `initData` проверяется на сервере (`backend/src/auth/telegram.ts`), дальше — токен сервера (JWT). Клиенту не доверяем: каждое тело запроса проходит схему zod (`backend/src/lib/validation.ts`), права — по пользователю из токена (`routes/access.ts`).
- Запись принимается, только если её начало есть в `freeSlots()`; пересечение двух действующих записей мастера запрещает сама база (`EXCLUDE` в миграции) — даже при одновременных запросах.
- В записи хранится снимок услуги (название, цена, длительность, валюта): мастер может поменять или удалить услугу, а история и выручка не меняются. Деньги — целые числа в валюте мастера.
- Время хранится в UTC (`timestamptz`), показывается в часовом поясе мастера. Телефон — только E.164.
- Какие данные храним и зачем — `docs/data-model.html`; новое поле в базе дописываем туда же.

## 8.1. Бэкенд (`backend/`)

- Схема — только SQL-миграции `backend/migrations/NNNN_*.sql` (применяются при старте по порядку, записаны в `schema_migrations`; применённую не меняем — пишем новую). `src/db/schema.ts` повторяет поля для Drizzle.
- Импорты: свой код — `~/` (`~/routes/...`), общий код фронта — `@/` (`@/utils/slots`, `@/api/types`, `@/utils/phone`). Логику, которая есть на фронте (слоты, телефон, нормализация данных), не копируем — импортируем.
- Маршруты — по разделам в `src/routes/` (`auth`, `masters`, `services`, `appointments`, `feedback`), подключаются в `app.ts`. Ответы — в типах фронта (snake_case, как `@/api/types`), перевод строк базы — `lib/mappers.ts`.
- Ошибки — `HttpError` (`lib/errors.ts`): статус + код (`slot_taken`, `not_cancellable`); фронт различает их по статусу.
- Зависимости приложения (база, часы `now`, бот) передаются в `createApp`: тесты подставляют PGlite в памяти и свои часы. Сценарии API — `backend/test/*.test.ts`.

## 9. Разработка

- В браузере при `npm run dev` вне Telegram включается режим просмотра: выбор «мастер / клиентка», тестовый пользователь. Если сервер не запущен, пользователь и данные подставляются локально (`mockRepo`). В обычной production-сборке этого нет.
- Демо для телефона — GitHub Pages: сборка с `VITE_DEMO=1` (режим просмотра без бэкенда, данные в браузере) и `BASE_PATH=/<репозиторий>/`, выкладывает `.github/workflows/pages.yml` при пуше в `main`. Проверка режима — только `PREVIEW_MODE` / `DEMO_BUILD` из `@/demo`, не `import.meta.env.DEV`. Пути к файлам из `public/` и база роутера — от `import.meta.env.BASE_URL`, не от корня `/`.
- Бэкенд с `NIDOKI_DEV_AUTH=1` пускает тестового пользователя. На проде не включать.
- Чистые функции из `src/utils` покрываем тестами vitest рядом с файлом (`hours.test.ts`), запуск — `npm test`.
- Перед завершением задачи: во `frontend/` — `npx vue-tsc --noEmit` и `npm test`, в `backend/` (если трогали его или общий код) — `npm run typecheck` и `npm test`, всё без ошибок.

## Открытые вопросы (подумать позже)

- **Как разводить мастера и клиентку без экрана выбора роли.** Сейчас экран «Я мастер / Я клиентка» есть только в `npm run dev` в браузере, в проде его нет. В проде роль определяется так: открыли по ссылке с `startapp=<slug>` — это клиентка; открыли из меню бота без параметра — это мастер (онбординг или кабинет). Что продумать:
  - клиентка открыла бота без ссылки — сейчас она попадёт в онбординг мастера; нужен экран «Мои записи» или вопрос «Ты мастер?»;
  - мастер сама открыла свою ссылку — показать страницу записи как клиентке или предложить кабинет;
  - защита маршрутов `/m/*`: пускать только при наличии записи в `masters`, иначе редирект.
